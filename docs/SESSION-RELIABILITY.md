# Configure session reliability candidate

This candidate continues the complete 22-file X11 candidate based on `5b13848`.
The physically verified X11 `Qt.Tool`/transient-parent fix and the X11 Meta+X
ordering correction are preserved. Taskbar text ghosting remains deferred.
No installation, login, compositor, shortcut or power-action changes are made.

## Findings

`Service::Edit()` previously started the editor with the backend's inherited
environment and returned `startDetached()` immediately. This reports successful
process creation, even when Qt subsequently aborts before creating a window.
The backend has a five-minute *idle* lifetime; ongoing menu requests renew it.
It has no graphical-session lifetime binding. A surviving backend can therefore
retain an earlier login's display/authentication state.

The activation entry generated by `native/packaging/installer.cpp` contains the
native executable and service arguments, without display or authentication
values. A newly activated backend inherits the user bus/activation environment.
Thus a fresh process can also have stale values. Direct `--edit` dispatches to
the editor and previously inherited its invoking process's environment.

The physical observation of an obsolete `XAUTHORITY` and the successful manual
environment-import/restart workaround are consistent with these paths. Available
physical evidence does **not** distinguish a surviving backend from a newly
activated stale one, or identify the exact KDE startup ordering that caused it.
Both paths are exercised independently by the new isolated regression tests.
An actual Qt XCB connection failure also now produces an error instead of a
successful `Edit` reply.

KDE's `plasma-plasmashell.service` is a `Type=dbus` service owning
`org.kde.plasmashell`, with `PartOf=graphical-session.target`. The inspected Plasma
6.3.6 unit starts after `plasma-ksmserver.service` and `plasma-kcminit.service`.
Binding OPM to that target could limit its lifetime, but would not refresh an
already-running process or correct stale activation variables in a new one.
An autostart environment import also cannot change existing process environments
and adds ordering dependence. This candidate uses the live Plasma owner on each
request instead; it does not change KDE units or import global variables.

## Change

The editor executable now starts with a Qt Core coordinator. Before initializing
Qt GUI, it resolves the current `org.kde.plasmashell` unique owner, obtains its
PID/UID from the same user bus, requires the current UID, and reads only an
allowlist from `/proc/PID/environ`. It verifies the owner/PID again after reading.
No environment is cached. Missing graphical keys remove obsolete inherited
values; Qt uses `xcb` for X11 and `wayland` for Wayland. Application configuration
paths and unrelated inherited settings remain unchanged. Authentication files
and cookies are never read or logged.

Without a Plasma owner, a D-Bus request uses its authenticated requester's
environment, while a direct invocation uses its own environment. Invalid session
data gives an actionable error. Explicit offscreen/minimal `--smoke-test` runs
remain available for development. Ordinary Configure requests cannot silently
select a stale offscreen backend. Fresh direct-launch activation tokens are
preserved when the invoking and resolved sessions match; cached backend or
Plasma startup tokens are not reused.

The coordinator starts a graphical child of the same editor executable. Only
after a visible, exposed `QQuickWindow` renders its first frame does it acknowledge
readiness. The backend delays the original `Edit` reply until that acknowledgement,
checking both a per-request random token and the coordinator's D-Bus PID. Early
exit, crash, missing executable, invalid session and startup timeout produce
`org.openpowermenu.EditorStartupFailed`. Plasma displays/logs the supplied error
instead of suggesting a backend restart. Direct invocation prints the failure
and exits unsuccessfully. Detailed Qt messages remain on stderr/in the journal.

The coordinator stays with its editor until the window exits, independently of
the backend. A backend exit does not close an already-open editor. There is a
15-second first-frame failure deadline and a 22-second backend acknowledgement
deadline, with no startup delay, retry loop, focus request or automatic restart.
Only the coordinator's own unready child is stopped on a first-frame timeout.
No additional installed binary or persistent service is introduced.

This relies on Linux procfs access to a same-user Plasma process and targets the
Plasma instance owning the name on that user bus. Restricted procfs or a session
owner changing during startup produces an error. Simultaneous graphical sessions
sharing a single user bus are outside the tested login-switch matrix. Reading
the live Plasma process's initial environment is intentional: the stale backend
or activation manager is not the source of graphical state.

## Automated verification

Debian 13 isolated container, Qt 6.8.2, Plasma/KWin 6.3.6; these are not the user's
physical Manjaro Plasma/KWin 6.7.5 login tests.

- Existing Python suite: **502 passed, 8 skipped, 18 subtests passed**.
- Native CTest suites: **10/10 passed**, covering interaction, model, recovery,
  editor settings/UI, standalone menu, dependencies, packaging platform checks,
  session launch and real X11 editor startup.
- Existing private-bus native contract tests: **15/15 passed**.
- Disposable installation/rollback tests: **10/10 passed**, including the actual
  1.0.1 installer from commit `3405848`, activation failure rollback, interrupted
  installation, settings preservation, unrelated service ownership and recovery.
- New launch tests exercise X11→X11, X11→Wayland, Wayland→X11 and six successive
  session-owner replacements while the backend PID stays constant; fresh backend
  activation from a deliberately stale bus; direct dispatcher and D-Bus `Edit`;
  removal of stale keys; config-path preservation; requester fallback; early exit,
  crash, clean exit without readiness, timeout, spoofed readiness and backend exit.
  Diagnostics are default off and checked for environment-secret exclusion.
- Actual Qt editor first-frame acknowledgement and direct dispatcher launch pass
  under Xvfb/X11 and an isolated virtual KWin Wayland compositor. Actual invalid
  X11 display initialization fails correctly for both D-Bus and direct invocation.
- Explicit headless editor smoke test passes. The production installer and
  dispatcher sources, configuration files and rollback layout are unchanged.

The initial test container had umask `0000`, which an existing dependency-review
test correctly rejected as unsafe directory permissions. Tests were rerun with
the repository's documented `umask 022`; no production permission check was relaxed.

Reproduce in a disposable build environment with the repository's native build
dependencies, Python 3, `dbus-daemon`, `dbus-run-session`, `busctl`, Xvfb and xauth:

```sh
umask 022
cmake -S . -B /tmp/opm-session-build -G Ninja -DOPM_BUILD_PACKAGE=ON -DOPM_INSTALL_TEST_HOOKS=ON
cmake --build /tmp/opm-session-build --parallel 2
QT_QUICK_CONTROLS_STYLE=Basic ctest --test-dir /tmp/opm-session-build --output-on-failure
dbus-run-session -- python3 native/tests/contract.py \
  --binary /tmp/opm-session-build/native/open-power-menu-native \
  --probe /tmp/opm-session-build/native/native-launch-probe
```

For an existing **isolated test display**, including virtual KWin Wayland:

```sh
python3 native/tests/editor_launch.py --build /tmp/opm-session-build/native --real-gui \
  EditorLaunch.test_real_editor_first_frame_via_dbus_and_dispatcher
```

The launch harness creates its own buses, session-owner fixtures, settings and
activation entries. Mock session changes prove environment selection, not real
logout/login behavior. No graphical session restart is part of the correction.

## Physical acceptance, still pending

After an explicitly authorized installation of the matching candidate binaries
and widget, use the normal login screen to test fresh X11, fresh Wayland,
X11→X11, Wayland→X11, X11→Wayland, and several consecutive repetitions. Do not
import activation variables or terminate the backend between attempts.

At each login, open Configure first from the OPM menu, close it, then run
`open-power-menu --edit`. Confirm the window is visible and usable, closing it
works, and menu preferences, backups, shortcuts and launcher visibility remain
intact. Exercise the already-running backend by reopening Configure after menu
use. For natural on-demand activation, leave OPM unused for its five-minute idle
lifetime and repeat. Separately retain the existing flyout/Meta+X acceptance
checks; taskbar ghosting is not an acceptance claim for this patch.

Optional per-invocation diagnostics, with no environment import or restart:

```sh
OPM_SESSION_TRACE=1 open-power-menu --edit 2>&1 | tee opm-configure-session.log
busctl --user call org.openpowermenu.Service /OpenPowerMenu org.openpowermenu.Service Edit
journalctl --user --since '10 minutes ago' --no-pager | \
  rg 'Configure|open-power-menu|qt.qpa|QQmlApplicationEngine' > opm-configure-journal.log
```

The trace records UTC timestamps, source owner, selected session type, display
names, authentication **path**, and first-frame success/failure. It does not dump
environment variables, authentication contents or startup tokens. The temporary
`OPM_SESSION_TRACE=1` setting applies only to that direct invocation. D-Bus failure
details and Qt startup errors are available without enabling tracing. The trace
does not activate, raise or refocus windows.
